# Pull Request 워크플로우

> ⚠️ **작성 원칙**: 본인이 아닌 **팀원이 읽기 쉽게** 작성합니다. 맥락 없는 동료가 이 PR만 읽고 변경 의도와 검증 방법을 파악할 수 있어야 합니다.  
> ⚠️ **사용자 승인 없이 `gh pr create`를 실행하지 않습니다.**

## 1단계: 사전 확인

아래를 **병렬**로 실행:

- `git status` — working tree clean 여부, 원격과의 ahead/behind
- `git branch --show-current` — 현재 브랜치명
- `git log <base>..HEAD --oneline` — base 대비 누적 커밋 (예: `git log develop..HEAD --oneline`)
- `git diff <base>...HEAD --stat` — 변경 파일 요약 (3개 점, merge base 기준)

### Base branch 판별
- 이 저장소의 일반적인 흐름: **feature/work 브랜치 → `develop` → `master`**
- 따라서 기본 base는 **`develop`** (확실치 않으면 사용자에게 확인)
- 긴급 배포(`[Hotfix]`)라면 base가 `master`일 수 있음 — 반드시 확인

### Push 상태
- `git status`에 "Your branch is ahead of" 가 있거나 원격에 브랜치가 없으면 **먼저 push 필요**.
- **자동으로 `git push` 하지 않고 사용자에게 안내**: "먼저 `git push`로 원격에 올려주세요. 그다음 PR 생성 진행할게요."

## 2단계: 제목 작성

**형식**: `[Prefix] 한 줄 요약`

- `prefix`는 `git-commit` skill의 12종 컨벤션과 동일하게 사용.
- 누적 커밋이 여러 성격이면 **가장 주된 작업의 prefix** 선택. 애매하면 사용자에게 확인.
- **70자 이내** 권장 (GitHub에서 잘리지 않게).
- 내부 slug, 커밋 해시, 티켓 번호만 들어간 제목 금지.

**좋은 예시**
```
[Feature] 인증 토큰 검증 및 API 요청에 적용
[Fix] 주문 취소 시 재고 복구 누락 수정
[Docs] Claude Code skill 구조 도입
[Chore] MySQL 8.0.44 업그레이드 및 의존성 정리
```

**나쁜 예시**
```
fix bug                              ← prefix 없음 + 정보 없음
[Feature] ABC-123                    ← 티켓 번호만 있음, 내용 모름
[Feature] UserService 수정           ← 구현 세부사항(파일명)만 있음, 결과 모름
```

## 3단계: 본문 작성

### 기본 템플릿 (필수)

```markdown
## 개발 내용
- (변경한 핵심 작업을 **결과 기준**으로 bullet)
- (구현 디테일이 아니라 **"무엇이 달라졌는지"**가 드러나게)

## 참고사항
- (리뷰어에게 알릴 맥락: 후속 PR 예정, 의도적으로 제외한 것, 알려진 한계 등)
- 특별한 참고사항이 없으면 섹션을 비우지 말고 `- 없음` 이라고 명시
```

### 선택 섹션 (해당될 때만 추가)

```markdown
## 테스트 방법
- (리뷰어가 로컬에서 검증 가능하도록 재현 스텝, curl 예시, 시나리오)

## 영향 범위
- **API**: (신규/변경된 endpoint, Swagger 명세 변화)
- **DB**: (엔티티 추가/변경, 수동 마이그레이션 필요 여부)
- **환경 변수**: (신규/삭제된 env var, 배포 전 설정 필요)
- **배포**: (특별한 배포 순서, 롤백 주의점)

## 관련 이슈 / PR
- Closes #123
- Related: #456
```

### 작성 체크리스트
- [ ] 제목에 prefix + 결과 요약 있음 (70자 이내)
- [ ] 개발 내용이 **"무엇이 달라졌는지" 중심**이고 파일명 나열이 아님
- [ ] 참고사항에 리뷰어가 알아야 할 사항을 검토 (없으면 `- 없음`)
- [ ] API endpoint 변경 있으면 → `영향 범위` 섹션 필수
- [ ] DB 엔티티/마이그레이션 변경 있으면 → `영향 범위` 섹션 필수
- [ ] 신규 env var 있으면 → `영향 범위` 섹션 필수
- [ ] 비UI/백엔드라도 **재현·검증 방법이 필요한 변경**이면 → `테스트 방법` 섹션 추가

## 4단계: 사용자 승인 대기

아래 형식으로 제시하고 **명시적 승인**(`진행`, `OK`, `그대로`)까지 대기:

```
### Base branch
develop  (자동 추론, 변경 필요 시 알려주세요)

### PR 제목
[Feature] 유저 회원가입 API 추가

### PR 본문
## 개발 내용
- ...

## 참고사항
- ...
```

- 수정 요청 시 제목/본문/base를 다시 작성해 재제시.

## 5단계: gh pr create 실행

```bash
gh pr create --base develop --title "[Feature] ..." --body "$(cat <<'EOF'
## 개발 내용
- ...

## 참고사항
- ...
EOF
)"
```

- 실행 후 출력된 **PR URL**을 사용자에게 전달.
- 생성 실패 시(push 안 됨, base branch 문제 등) 원인 분석 후 사용자에게 안내.

### ⚠️ HEREDOC 안에서 백틱(`` ` ``) 이스케이프 금지

- `<<'EOF'`(작은따옴표 delimiter)는 bash에서 **literal mode**로 동작하므로 변수 치환·명령 치환·백슬래시 해석이 일어나지 않는다.
- 따라서 PR 본문 안의 인라인 코드·코드 블록의 백틱은 **그대로** 사용할 것.
- `` \` `` 처럼 이스케이프하면 GitHub PR 본문에 그대로 `\`` 가 출력돼 마크다운 렌더링이 깨진다.
- 코드 펜스(백틱 3개)·SQL 블록·inline `code` 모두 이스케이프 없이 원본 그대로 heredoc 안에 두면 된다.
- 참고: `<<EOF`(무따옴표) 는 명령 치환을 하므로 백틱을 쓰려면 반드시 이스케이프해야 한다. **PR 본문용 heredoc은 항상 `<<'EOF'` 로 열 것.**

잘못 이스케이프한 PR 본문이 이미 올라갔다면 `gh pr edit <num> -R <owner/repo> --body "$(cat <<'EOF' … EOF)"` 로 재설정.

## 6단계: 후속 안내

- PR URL 전달과 함께 **남은 작업 체크**:
  - 리뷰어 지정 필요 여부
  - CI 상태 확인 필요 여부
  - 추가로 말씀드릴 맥락 (후속 PR 예정 등)

## 금지 사항

- ❌ **사용자 승인 없이 `gh pr create` 실행**
- ❌ **자동 `git push`** — 사용자가 직접 push하도록 안내
- ❌ 컨벤션 외 prefix 사용 (`git-commit` skill의 목록 준수)
- ❌ 빈 본문 / "WIP" / "자세한건 말로 설명" 같은 정보 없는 PR
- ❌ 제목에 커밋 해시/내부 slug/티켓 번호만 있는 형태
- ❌ 본인만 이해할 수 있는 용어·약어 남발 (팀원 기준으로 서술)
